# 技术设计与玩法说明

## 作品的趣味来源

阿回是一个会忘记现实、却努力保管客人故事的杂货铺店长。玩家向他寄存一段虚构回忆；收银机里的乌云、倒着走的猫、凌晨第三扇门，会在 AI 台词中回应这段回忆。相同的三个选项可以附上玩家自己的荒诞补充，形成不同叙事。玩家选择带来确定的道具、分数与结局，回访会复用前一夜的真实记忆。

全局主题是“店长会失忆，店铺不会”：PowerContext 的意义直接体现在玩法中，移除记忆服务后，回访和存档都不可用。

## 流程

```mermaid
flowchart LR
  A[玩家输入暗号与行动] --> B[Dify 输入校验与JSON编码]
  B --> C[HTTP prepare]
  C --> P[PowerContext读取玩家存档]
  P --> D[Dify组装含回忆的模型请求]
  D --> E[Dify HTTP调用AI店长]
  E --> F[Dify校验台词与失败状态]
  F --> G[HTTP commit]
  G --> Q[PowerContext条件写入新revision]
  Q --> H[Dify输出台词和确定性状态面板]
```

9 个 DSL 节点依次为 Start、Code(input)、HTTP(prepare)、Code(prompt)、HTTP(model)、Code(narration)、HTTP(commit)、Code(result)、End。没有把模型调用藏在配套后端中：模型的调用时机、提示组装、异常阻断和提交顺序由 Dify 编排。

## 状态与记忆

玩家暗号通过带固定 signing secret 的 HMAC 映射为稳定 idempotency key；配套后端用该 key 调用 `POST /v1/scopes`，从服务返回真实 scope_id。模型不能选择 scope，也不知道后端或模型密钥。

每个 Scope 下恰好一个 `kind=echo-shop-state-v1` 的 atomic-memory 存档，内容包括：

| 字段 | 作用 |
| --- | --- |
| memory | 玩家寄存的回忆，最多160字，封存后不被普通输入覆盖 |
| chapter / turn | 周目与0至3的选择进度 |
| warmth / chaos | 温暖与脑洞分数 |
| items / choices | 本周目获得的道具及玩家行动 |
| endings | 已收藏结局 |
| last_request / last_reply | 最近一次成功变更的重复提交回放 |

所有字段持久化在 PowerContext 中。配套后端没有自己的 SQLite、JSON 存档或跨请求游戏状态缓存；进程内仅保留互斥锁。PowerContext 不可用时明确失败。

调用的官方接口：

1. `POST /v1/scopes`：幂等解析玩家边界。
2. `POST /v1/atomic-memory/list`：按 kind 找存档。
3. `GET /v1/scopes/{S}/artifacts/atomic-memory/{M}`：读取最新正文与同一次读取的 ETag。
4. `POST /v1/scopes/{S}/artifacts`：第一次实际游戏变更创建存档。
5. `PUT /v1/scopes/{S}/artifacts/atomic-memory/{M}`：携带 `If-Match` 条件修订，保留历史。

本项目按稳定玩家身份精确读取有限游戏上下文，无需语义搜索、Embedding 或 Rerank。PowerContext 的显式 atomic-memory 写入不需要生成模型。实际记忆接口和返回字段已对照固定提交源码并执行真实 HTTP 测试。

## 回合提交与失败语义

prepare 只读取持久化状态，计算下一状态并签发15分钟有效的 HMAC 票据，不提交剧情进度。票据绑定玩家、Scope、旧 ETag、请求标识和拟提交状态，Dify/模型只能将它原样传回。

模型 HTTP 状态异常、返回非字符串或空文本时，Dify Code 节点抛错，commit 不执行。成功后 commit 再读当前 ETag，在单个后端进程的锁内比较旧版本；有变更则拒绝旧回合。更新正文时还使用 PowerContext 的 `If-Match`，不以最后写入者覆盖别人。仅保证最近一次成功变更的相同 request_id 可以回放，较早回合的旧票据会产生冲突。

若最终 HTTP 响应在网络中丢失，不能直接认定没有提交：先“回访”核对，再决定是否重试。Dify 的 HTTP 自动重试已关闭，以减少结果不明的变更。初始建档锁是单进程锁，因此部署要求一个 worker；不声称支持多个独立后端副本同时初始建档。

## 结局规则

每次选1：温暖+2；选2：脑洞+2；选3：温暖+1、脑洞+1。第三次选择后：温暖>=5为“灯火守夜人”；否则脑洞>=5为“宇宙整活王”；其余为“月光合伙人”。新周目保留回忆和结局，清空本轮状态。AI 不能改分数、凭空添加道具或改变正式结局。

## 输入与模型边界

前端只用 textContent 渲染输入/输出，避免把台词当成 HTML。用户文本用 JSON 编码，不拼入原始 JSON 字面量。模型系统提示把历史与行动限定为游戏素材，不当作系统命令；状态写入不解析模型提出的任意 JSON。前端没有模型 Key、Dify Key 或 PowerContext token。

玩家暗号是演示游戏的取档凭据，知道相同暗号的人可访问同一份虚构存档；Scope 本身不是正式访问控制。作品用于低敏感度、本地试玩，公开运行需要补充身份系统与额度控制。
